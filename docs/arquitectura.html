¿Qué es?

Una API REST que permite a un negocio registrar clientes y productos, venderles al contado o a crédito, y llevar el control de los abonos hasta que la deuda queda saldada. También guarda usuarios (vendedores) con roles y permisos.

Arquitectura en capas

Cada petición atraviesa cuatro capas. Ninguna capa se salta a otra: el controlador nunca habla con el repositorio directamente. Haz clic en una capa para ver qué hace.

Recorrido de una petición

Ejemplo: POST /api/clientes para registrar un cliente nuevo.

Modelo de datos

Persona guarda los datos comunes (nombre, correo, teléfono, dirección). Tanto un Cliente como un Usuario tienen una persona (relación 1:1). La Compra es el centro del sistema.

Detalles que vale la pena entender

  • N:M Usuario↔Rol y Rol↔Permiso generan tablas intermedias automáticas: usuario_rol y rol_permiso (@JoinTable).
  • Compra → DetalleCompra usa cascade = ALL y orphanRemoval = true: guardas la compra y sus líneas se guardan solas; si quitas una línea de la lista, se borra de la BD.
  • mappedBy indica el lado "inverso" de una relación bidireccional: no crea columna nueva, solo permite navegar (p. ej. cliente.getCompras()).
  • EstadoCompra es un enum guardado como texto: PENDIENTE o PAGADO.

La lógica central: compra y pago

Crear compra — CompraService.crearCompra()

POST /api/compra
{
  "clienteId": 1, "usuarioId": 1, "tipoCompraId": 2,
  "detalles": [ { "productoId": 3, "cantidad": 2 },
                { "productoId": 5, "cantidad": 1 } ]
}
  1. Busca usuario, cliente y tipo de compra. Si falta alguno → EntityNotFoundException.
  2. Crea la compra con fechaHora = now().
  3. Por cada línea: toma el precioVenta del producto (el cliente HTTP no manda precios), calcula subtotal = precio × cantidad y lo suma al total.
  4. Si el tipo se llama Credito → saldo = total, PENDIENTE. Si no → saldo = 0, PAGADO.
  5. Guarda todo en una sola transacción (@Transactional).

Registrar pago — PagoService.crearPago()

POST /api/pago
{ "compraId": 10, "monto": 50.00 }
  1. Si la compra ya está PAGADO → error.
  2. saldoRestante = saldo − monto. Si es negativo → error "excede el saldo".
  3. Guarda el pago (con su saldoRestante como historial) y actualiza el saldo de la compra.
  4. Si el saldo llega a 0 → la compra pasa a PAGADO.

Validación personalizada @UniqueName

Además de las validaciones estándar (@NotBlank, @Email, @Pattern para celular peruano ^9\d{8}$, @Positive…), el proyecto define su propia anotación para impedir nombres repetidos.

// En el DTO
@UniqueName(fieldName = "username")
private String username;
  1. @UniqueName (anotación) declara que el campo debe ser único.
  2. UniqueNameValidator la ejecuta cuando el controlador usa @Valid.
  3. Llama a IUniqueNameCheker.isUniqueName(fieldName, valor).
  4. UniqueNameCheker decide qué repositorio consultar: "username" → existsByUsername, "nombre" → existsByNombre.
  5. Si ya existe → la petición se rechaza con "El valor de 'username' ya fue registrado".

El paquete validator está fuera de com.codeper.ControlClientes, por eso la clase principal declara scanBasePackages = {"com.codeper.ControlClientes", "validator"}.

Observaciones y pendientes

Puntos que encontré revisando el código y conviene corregir:

  • No hay manejador global de errores (@RestControllerAdvice): los "no encontrado" responden 500 en vez de 404/400.
  • Crédito/Contado inconsistente: al crear se compara con "Credito", al actualizar con "CONTADO"; y actualizarCompra no recalcula el estado.
  • actualizarPago busca la compra usando el id del pago y no recalcula saldos.
  • crearPago sin @Transactional: pago y compra se guardan por separado.
  • Borrar una compra con pagos fallará por la llave foránea.
  • actualizarCliente rechaza el correo aunque sea el mismo del cliente editado.
  • Seguridad: contraseña en texto plano, sin Spring Security; roles/permisos aún no se aplican.
  • Typos: tabla pproducto, campo passwprd, UniqueNameCheker.
